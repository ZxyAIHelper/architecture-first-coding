# 先设计架构再处理代码

先确定分层、职责、权威所有者、契约和实际依赖，再实现。设计须能指导编码并对照代码验收；目录树或系统名单不能替代设计。

## 按范围执行

- **模块内小改动**：核对受影响的职责、所有者、接口和调用方，简短说明后直接实施；不强制新建文档、接口层或测试工程。
- **新增系统、跨模块功能、状态/接口/生命周期变化**：先完成设计决定，再编码。记录在项目已有计划或架构文档中；无文档要求时可在回复中给出精简设计。只要求设计或分析时不擅自实现。
- **既有项目**：先小范围读取相关规范、入口和调用方，对照实际实现。遵守现有架构；发现冲突须指出并按项目流程调整设计，不能因“已有结构”或“测试全绿”继续扩大已发现的越界。只修当前范围，其他问题记录为后续工作。

## 默认架构与硬约束

建议所有代码按五层职责设计，从高到低为：**接口层 → 应用层 → 核心层 → 数据层 → 平台层**。层是职责边界，不强制五个目录、类或空壳转发；既有功能模块内也可分层。已有其他明确架构时先说明职责映射及约束差异，不自动重构全项目。

- **禁止低层调用或源码依赖上层**，包括导入、类型引用、接口实现、注册回调、反射、事件派发及服务定位器形成的隐藏反向依赖。源码依赖与运行时调用分别检查，依照分层参考中的允许关系落地。
- **状态和业务规则有唯一权威所有者**。UI只转换输入、展示权威结果，可拥有焦点/选择等局部状态。查询不改权威业务状态，不泄漏可写内部引用；缓存须明确失效策略。
- **共用能力可复用且有归属**。按职责归入所有使用方都能合法依赖的层，通过窄接口共享；不复制公式、不建立全局可写上下文，也不靠 shared/common 绕开分层。
- **三方库先核对选型条件，再接入**。验证所选版本对目标平台、架构、运行时及交付方式的支持，并核验许可证与项目用途和分发方式兼容、义务可履行；覆盖传递及原生依赖，记录来源和证据。接入仍遵守分层，不能通过三方回调调用上层业务。
- **按真实职责拆分**。页面、规则、事务、I/O或生命周期可独立变化时形成边界；`api/main/manager`不是集中全部实现的理由。行数和目录整齐不能单独决定拆分。

## 执行与交付

1. 小范围定位规范、相关模块、入口及调用方，确定现有层级与状态所有者。
2. 对适用任务给出具体设计：职责/层级、状态与生命周期、关键接口名称及必要字段/单位/错误、允许依赖、主要流程、失败恢复和验证方式，不能推迟为“后续再定义接口”。
3. 按设计实施；接口、所有权或依赖变化时先同步设计与调用方。名称说明职责，保留既有编号约定；必要注释说明设计意图。
4. 按风险验证真实调用、数据流、共享能力和失败状态。静态检查、语义评审、行为验证分别报告；公开API、目录/owner检查或测试全绿不能单独证明架构合理。
5. 简述实际决定、修改位置、验证与遗留问题。小改动采用适度验证，不写复述实现的测试；设计完成后在用户已授权范围内继续，不额外设置统一审批门禁。
