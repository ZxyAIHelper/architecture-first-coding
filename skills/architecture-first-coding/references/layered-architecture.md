# 五层职责与调用约束

适用于新项目、架构设计、跨层修改和依赖评审。先标明模块属于哪层，再检查源码与真实调用；不能仅凭目录判断。

## 层级与职责

从高到低为接口、应用、核心、数据、平台。这里的“接口层”指用户/外部入口，和各层自己的公开 API、端口不是同一个概念。

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 接口层 | GUI、HTTP、CLI、设备输入；解析请求、调用用例、展示结果；焦点和选中项等局部状态 | 业务公式、直接改业务账本、直接查询数据库代替用例 |
| 应用层 | 用例、事务流程、阶段转换、跨模块协调；应用会话生命周期 | 重算核心规则，把所有系统内部状态汇总为全局可写对象 |
| 核心层 | 领域模型、权威运行状态、业务约束与公式；领域模型和数据记录间的语义映射 | UI、SQL、文件格式解析、网络SDK及引擎对象操作 |
| 数据层 | 记录/配置读写、存储契约、缓存、格式校验、序列化、迁移及数据输出适配 | 决定业务资格、伤害、定价或流程；引用核心领域类以操作其状态 |
| 平台层 | OS/引擎/运行时适配、文件、数据库驱动、网络、时钟、日志、纯技术工具、三方SDK封装 | 引用项目上层模块，保存业务账本或决定业务流程 |

同一个功能模块可以包含多层；小工具可在少量文件内分清职责，不创建空壳层。依赖检查以职责为准，不能通过移动目录或改 owner 降低某段代码的实际层级。

## 允许的依赖

箭头表示主动调用或源码依赖；禁止反向。以下是默认白名单，不表示每层都必须依赖所有列出的对象：

| 调用方 | 允许依赖 |
| --- | --- |
| 接口层 | 应用层；输入/显示所需的平台技术适配 |
| 应用层 | 核心层；用例所需的数据层公开能力和平台技术能力 |
| 核心层 | 数据层公开记录/存储契约；不含业务语义的平台纯技术能力 |
| 数据层 | 平台层 |
| 平台层 | 语言标准库与受管理的外部依赖，不依赖项目上四层 |

- 业务路径优先沿 `接口 → 应用 → 核心 → 数据 → 平台` 展开；不为凑齐链条增加转发。跨过某层调用更低层须在设计中列明用途，不能跳过权威校验。例如接口层不得直接调用数据层扣款；应用层可以读取技术性导出配置，但定价仍归核心。
- 表内的公开能力也须限制到本次所需接口，不能注入全量系统字典或允许任意模块解析全局容器。
- 同层模块只通过明确接口进行单向、无环依赖，禁止访问私有状态。出现互相调用时，拆出同层共有职责，或交由已有上层编排；平台层不能再借助项目更低层解决自身循环。
- 启动装配是最外侧入口：可引用各层创建和注入对象，不保存领域状态、不做业务决策；不得被低层反向访问。

## 源码依赖与运行时调用都必须向下

低层不能导入、继承或实现上层定义的类型/接口，也不能持有上层对象、调用上层业务回调、反射查找上层服务或借事件总线执行上层处理器。即使没有静态 import，也可能构成向上调用。

本技能采用严格五层方向，不能把另一种架构中的“数据适配器实现核心/应用声明的端口”直接搬来，称为分层合规。存储能力的窄契约和数据记录定义在数据层，其实现依赖平台；核心通过该公开契约读写并映射自己的领域模型。数据层不知道领域类，也不持有核心实例。更换存储实现时保持数据层契约稳定。

双方均需使用的协议只含必要的数据结构、标识、单位与结果形状，归入双方能合法依赖的较低层。不要把核心算法下移到协议或平台以规避依赖限制。

- 下层返回结果、抛出已约定错误，或完成调用方等待的异步结果，是原调用的结果通道，不是主动调用上层业务。
- 需要持续通知时，下层提供事实队列/结果查询，由上层主动消费并决定后续动作；不要让下层注册并派发上层业务回调。成功事实在对应提交后产生，重试相关事实须有必要的标识及去重语义。
- OS、引擎或框架将输入调度到接口层入口属于外部入口机制；业务处理器归接口层。自有平台模块不得因此引用或调度上层业务处理器。三方SDK回调只进入平台适配器，转成结果或可查询事实供上层消费。
- 阶段、时钟、会话ID、权限结果由调用方显式传入，或查询其合法依赖的能力；不让底层回查总协调器。

## 一条实施示例

库存工具中：GUI/CLI（接口）调用库存用例（应用），用例调用库存规则与状态（核心），核心使用库存记录库（数据），记录库使用SQLite适配（平台）。两入口消费核心给出的估值，不各算一次。PDF输出可由应用取得权威报表快照，调用数据层输出适配，再使用平台层PDF SDK封装；数据与平台都不引用库存核心类。

设计中写清每条实际边的用途；验收同时检查导入/类型、注入对象、同步回调、事件派发和关键链路的运行行为。既有项目发现反向依赖时，限定当前改动的修复范围并记录遗留，不以旧代码存在作为新增越界的理由。
