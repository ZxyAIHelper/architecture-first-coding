# 跨模块复用与三方管理

涉及共享能力、重复规则、全局状态或外部依赖时读取；具体层级遵循 [五层约束](layered-architecture.md)。

## 复用的归属

先找现有权威实现和公开接口，再决定复用或提取。多个模块需要相同能力时，提供一份可复用实现；共享的是明确职责，不是恰好相似的几行代码。

| 共用内容 | 应归属的位置 |
| --- | --- |
| 定价、伤害、权限等业务公式与判定 | 核心层的具体领域模块；调用方消费其结果 |
| 多入口共用的用例或事务流程 | 应用层公共用例 |
| 同类记录加载、格式校验、缓存和迁移 | 数据层公共能力 |
| 文件、时钟、日志、几何运算等无领域语义能力 | 平台层技术模块 |
| 通用控件、布局、交互行为 | 接口层组件 |

- 共享模块写明唯一维护者、公开接口、允许依赖与状态生命周期；按层和功能命名，例如数据层的记录读取能力，而非一个包揽所有事情的 `utils`。
- 同层多个模块复用时，可提取同层无反向依赖的公共模块，调用者单向依赖它；不同层共用时，放在所有调用者均可合法依赖的位置。若提取后必须认识调用方，就应调整职责或传入纯数据，而非加回调。
- 不能把业务规则搬到平台/数据层，只为让低层也能复用。由核心计算结果后传下去，或先纠正低层承担了业务决策的问题。
- 通用协议与值类型保持最小、稳定，不导入消费者。存储记录与领域模型含义不同时，核心进行映射；不强制所有层共用一个大DTO。
- 不通过共享可写单例复制库存、余额或其他权威状态。确需共享的状态须有唯一所有者，通过命令/只读查询访问，不能所有消费者随意改字段。
- 不把独立近似模型的公式差异悄悄合并：明确权威来源、差异和校准方式。生成器、编辑器、导出和运行时的共用输入契约要一致。

提取公共能力应由实际的多个使用方或明确复用需求驱动，不预建无人使用的插件框架。验证至少两个实际消费者共享相同规则结果，且修改公共实现不会要求消费方理解其内部结构。

## 三方依赖：选型与代码接入分开

三方管理首先确保库可用于项目目标：新增、替换、升级依赖，或目标平台/分发方式变化时，先读取 [库兼容性与许可证核验](third-party-selection.md)。记录许可证名称或封装一层SDK都不能代替选型结论。以下只说明获选依赖的代码组织。

**声明/版本管理**沿用包管理清单、锁文件及项目已有记录，注明依赖的用途、来源、直接/传递关系、版本约束和消费模块；已有记录能表达时不另建第二份清单。安装或升级按当前任务授权执行，不因为维护架构自动升级依赖。

**代码接入**按实际风险和语义隔离：

- SDK、引擎、原生库、数据库驱动、文件和网络操作的包装位于平台层。上层通过窄技术接口调用；客户端初始化、连接、线程、句柄、取消与关闭生命周期明确归属。
- 存储记录、内容格式及导出文档映射属于数据层；业务语义转换与决策属于核心/应用所属模块。平台只报告技术结果，不根据失败决定退款、胜负等业务动作。
- 外部类型、异常码、路径和配置从接入边界转换成项目自己的稳定结果；不要让SDK对象成为跨层DTO或权威领域状态。
- 回调、订阅与异步完成继续遵守禁止低层调用上层：平台接收SDK回调，只保存/返回技术结果，供上层等待或主动读取；不将业务Callable传给平台执行。
- 标准库或稳定、无状态的纯函数依赖无需逐函数制造转发包装，但要记录使用范围；属于项目代码的封装仍受层级约束，外部UI/引擎框架类型仅可留在必要的入口适配处。
- 需要随仓库保存的源码、二进制或补丁使用既有 vendor/third_party 约定，和自有代码区分；包管理器已管理的依赖不再复制一份。记录许可证/来源及本地补丁，避免直接修改无法追踪的安装目录。

升级时检查公开接口、数据格式、平台支持和错误语义；按影响验证适配器与关键调用方。宣称可替换前，用替身或另一实现验证边界，而不只看是否套了一层名为adapter的包装。
