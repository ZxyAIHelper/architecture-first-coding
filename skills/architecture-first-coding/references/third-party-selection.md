# 三方库兼容性与许可证

在选择、新增、替换、升级库，或目标平台、打包和分发方式改变时读取。重点是库能否用于项目，而不只是如何包装API。沿用项目依赖政策、许可白名单和既有清单；不为每个库增加审批流程或重复记录体系。

## 先明确使用条件

从项目现有配置与规格确认目标操作系统、CPU架构、引擎/语言/运行时版本、桌面/移动/Web等交付目标，以及开发工具、构建依赖、运行时依赖的不同使用范围。区分当前必需目标与未来计划，不擅自增加平台。

确认项目的预期用途、闭源/开源和商用要求、源码/二进制/服务交付方式、链接或打包方式，以及可履行的许可义务。缺失信息影响选型时，先查现有资料；仍无法推断的关键产品或授权决定再向用户说明，不因普通依赖维护反复请求确认。

## 跨平台支持：按版本和实际交付核对

| 核对项 | 必须明确的内容 |
| --- | --- |
| 目标组合 | 每个必需OS、CPU架构和运行时/引擎版本；不能仅写“跨平台” |
| 官方支持 | 所选库版本的官方支持矩阵、发布产物、构建说明及限制；区分官方支持与社区移植 |
| 原生/传递依赖 | 本地扩展、系统动态库、驱动、GPU/图形后端、编译工具链、可选后端及其支持情况 |
| 构建与安装 | 有无适配目标的包/二进制；源码构建是否需要额外工具，能否在已有CI及离线条件下复现 |
| 运行与分发 | 打包能否携带所需文件；动态加载、路径/文件名大小写、权限、沙箱及运行环境要求是否适用 |
| 实证 | 按风险进行目标环境下的最小导入、关键功能、构建或安装包运行检查；记录未测试目标 |

纯语言实现、包管理器能安装、支持某语言或开发机能运行，都不能单独证明全部目标可用。按实际使用的后端/功能确认支持，不把同一库其他后端的支持直接套过来。

为必需目标记录“官方声称的支持”与“项目实际验证”两列，附版本和来源；结论明确为已验证、需适配、未核实或不支持。不能把未测试写成通过，也不把官方说明当作安装包已实测。没有目标设备时，可完成官方材料及构建核对，注明运行验证缺口。

## 许可证：核对适用性和义务

核验所选版本实际发布包/源码中的LICENSE、NOTICE、官方许可说明及相关组件条款；包元数据、搜索摘要和“免费/开源”标签只能用于定位，不能作为最终依据。实际选库时优先核验官方当前材料，保留版本、来源和核对时间；已有本地固定版本材料可直接检查。

- 按项目真实用途核对使用、修改、商用、闭源、再分发及部署方式是否满足条款，确认与项目及已有依赖的许可安排能否兼容。
- 明确需要保留的许可文本、署名/声明、修改说明，以及可能适用的源码提供、链接/打包等要求；逐项落实到交付物或构建步骤，不能只写“许可证已检查”。不预设某类许可证总是允许或总是不允许。
- 覆盖随所选功能引入的直接/传递依赖、原生二进制、捆绑资源及可选组件，避免只看顶层库。多重许可、商业授权、版本差异和例外条款须明确采用哪一种依据。
- 缺失、冲突或含糊的许可材料标为未核实，不自行推定可用；先查证或选择满足条件的替代库。确有无法判断的关键条款时，标明待确认事项，不伪装成确定的法律结论。

## 形成可执行的选型结论

记录在现有设计、依赖清单或评审记录中，至少包含：库与版本、用途和消费层、官方来源、目标支持/实测矩阵、直接及相关传递依赖、许可证依据、兼容性结论、需履行事项及替代方案/未决项。小型依赖可用一段文字或少量表格，不强制建立SBOM工程。

优先选择满足当前必需平台和许可条件、维护状况适当、依赖成本可接受的方案。比较维护活跃度、运行时/引擎兼容、已知问题和替换成本；不要把最流行、最新或API最方便直接当作适用结论。关键条件未核实前不将该库描述为已获选并支持全部目标；可继续完成不依赖该选择的工作。

获选后沿用包清单/锁文件固定依赖关系，在相应层接入，按 [接入边界](reuse-and-third-party.md) 组织代码。升级或交付条件变化时重核受影响项。交付说明证据、已落实义务与剩余缺口；维护技能本身不意味着已审核项目现有全部依赖。
