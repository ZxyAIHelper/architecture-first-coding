# 设计产物与验证

新增系统、跨模块功能、状态/契约变化及完整架构验收时读取。模块内小改动只核对相关边界，避免固定流程膨胀。

## 实现前必须明确的决定

写入现有计划/架构文档；没有文档要求时可用回复中的精简设计。不为每次修改新建文档体系。影响实现的未知条件须指出，能合理推断的选择说明假设后推进。

| 决定 | 交付内容 |
| --- | --- |
| 职责/层级 | 模块名称、所在层、负责及不负责事项、对应需求和文件/组件；同层复用模块也标明归属 |
| 状态/规则 | 权威状态、唯一写入者、公式/决策所有者；派生数据、缓存及失效条件 |
| 生命周期 | 创建、持有、初始化、重置与释放；场景/请求/进程间存活范围 |
| 公开契约 | 关键命令/查询/事实的名称，必要输入输出字段、类型、单位、错误形式与提交语义 |
| 允许依赖 | 调用方→被调用方及用途；标出同步/异步/同层关系、注入能力、三方适配边界 |
| 主要流程 | 至少一条真实用例从入口到编排、规则/状态、I/O或呈现的链路；关键时序由谁保证 |
| 失败恢复 | 中途失败后已提交什么，如何回滚/恢复/重试，是否需要幂等、去重和并发控制 |
| 验证 | 每项关键边界/行为对应什么检查，不能验证什么；实际修改范围与遗留问题 |

关键跨模块接口至少给出简短签名或DTO字段示例，不能只列模块职责后写“再定义接口”。例如：`receive(operation_id, warehouse_id, sku, quantity) → Result<receipt_id, revision>`，同时说明数量单位、错误码、提交前校验与重复请求语义；不必穷举内部方法。

重要结构选择说明理由与代价，用一两个真实变化检验，例如新增同类内容、替换界面或失败后重试会修改哪些模块。不要把“支持扩展”当作无须证据的结论，也不扩展未要求的产品范围。

## 实现过程中的核对

- 规则只由权威所有者计算。界面、导出和工具展示明确标识的基础值或有效值，不重算价格、伤害、阶级选择或业务舍入；普通展示格式化允许。
- 命令由所有者校验并提交；查询不改变权威业务状态，不暴露可写内部引用。内部缓存允许按已声明的失效策略更新。
- 事务或跨模块操作明确部分失败和重试顺序，不假定每种外部系统都支持同一事务。成功事实在相应提交后发出；只在需要防重的链路要求事件/操作标识。
- 页面、规则、事务、I/O及生命周期可独立变化时形成职责边界；不要把全部实现收进一个公开入口，也不凭行数机械拆分。
- 外部调用、生成器、测试与工具同样说明所有者及层级；不因为不进入发行包就绕开规则。必要注释解释边界和设计意图。
- 接口、所有权或依赖变更时先更新设计及受影响调用方，再继续实现。保留现有命名规范，不擅自重命名全项目。

## 验证与证据

| 检查 | 应证明什么 |
| --- | --- |
| 源码边界 | 文件/模块层级、导入、类型引用、接口实现、允许依赖；下层不引用上层，公共模块无环 |
| 实际调用 | 注入对象、反射/定位器、回调及事件处理器的真实目标，不能只检查import |
| 语义所有权 | 唯一状态写入者、规则来源、显示与权威值一致；低层没有承担上层业务 |
| 行为 | 受影响的成功路径、相关失败/重复/竞争情境，及项目要求的确定性 |
| 复用与三方 | 实际消费者共享实现；外部类型与错误止于边界，依赖版本和生命周期可追踪 |

优先复用项目现有检查，针对风险选择验证，不为小改动建立测试工程，不编写只匹配文档用词或复述实现的测试。架构重构尽量保持外部行为，业务变化单独说明。

目录、owner、公开API调用或测试全绿只能证明相应检查覆盖的内容；不得单独据此宣布架构合格。交付分别说明静态检查、人工语义核对、行为验证及未执行项；只读设计评估不能冒充已实现产品的测试。设计完成后在用户已授权范围内继续，不额外增加统一审批门禁。
